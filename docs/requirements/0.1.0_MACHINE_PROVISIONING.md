# 0.1.0 — Machine provisioning

- **Status:** Accepted (2026-10-15). Captures what vizion does today plus the new selective-install need. Tool-agnostic; see ADR 0001 for the tooling and `0.1.0_CHEZMOI_DESIGN.md` for the design.

## Goals

1. Turn a fresh Mac into my working environment with one command and a few prompts.
2. Let each machine choose which parts it gets (personal Mac vs company laptop).
3. Make day-to-day maintenance cheap: adding a package or a config file is a one-line change, with no installer code.

## Functional requirements

### R1 — Bootstrap

- R1.1 One copy-pasteable command on a fresh Mac installs the prerequisites (Xcode Command Line Tools, Homebrew, the provisioning tool) and applies the setup.
- R1.2 Re-running it, or the apply command, on an already provisioned machine is safe (idempotent) and only changes what differs.
- R1.3 It does not need a Mac App Store sign-in unless the machine selected a group with MAS apps.

### R2 — Profiles and groups (new)

- R2.1 Packages, configs and setup steps are organised in **groups** (e.g. `core`, `dev`, `gui`, `personal`, `mas`).
- R2.2 A **profile** (`personal`, `work`) is a named default set of groups.
- R2.3 On first run the machine is asked for its profile, and can switch individual groups on or off. Answers are stored per machine, outside the repo, and not asked again.
- R2.4 Answers can be changed later and re-applied, adding the newly selected parts.
- R2.5 Configs can differ by profile through templating (e.g. git identity, GitHub Enterprise host), not by duplicating files.
- R2.6 Deselecting a group does not have to uninstall anything (removal is optional and explicit, e.g. `brew bundle cleanup`).

### R3 — Packages

- R3.1 Homebrew formulae and taps, casks (incl. fonts) and Mac App Store apps, each assigned to a group.
- R3.2 Language runtimes through asdf, pinned in `~/.tool-versions` (e.g. Node.js). No global npm packages: language servers, formatters and linters are installed by Mason inside the LazyVim config. No Neovim language providers (pynvim, `neovim` npm): plugins are Lua only.
- R3.3 Editor and shell plugins: oh-my-zsh, tmux plugin manager and its plugins, Neovim plugins for both configs (lazy.nvim restore from `lazy-lock.json`), VS Code extensions from a list in the repo.
- R3.4 Third-party code is fetched at install time, not vendored in the repo.

### R4 — Dotfiles and config directories

- R4.1 Manage the dotfiles still in use: `.zshrc` (owned by the setup, not created by an installer), `.zshrc.aliases`, `.zshenv`, `.gitconfig` (+ delta include), `.gitignore`, `.hushlogin`, `.tool-versions`.
- R4.2 Manage `~/.config/{nvim,nvim-legacy,tmux,git,karabiner}`, iTerm2 global prefs (read from the repo), iTerm2 Dynamic Profiles, and VS Code `settings.json` / `keybindings.json`.
- R4.3 Existing files are never silently overwritten: show a diff and ask (vizion currently skips them silently).
- R4.4 Editing a managed config and saving it back to the repo is a single, documented command. Files are copies by default (the tool's intended mode); symlinks are used only for files an app rewrites itself.
- R4.5 Configs, Neovim's in particular, stay in sync across machines through the git repo: push on one machine, pull-and-apply on the others. Files that apps rewrite (`lazy-lock.json`, `karabiner.json`, iTerm2 prefs) are picked up without a manual re-add.
- R4.6 Two Neovim configs side by side: the LazyVim-based config is the default (`nvim`), the previous config stays available as `NVIM_APPNAME=nvim-legacy` (alias `nvim-legacy`). Both are synced and both get their plugins restored on install.
- R4.7 VS Code settings and extensions come from the repo, never from VS Code Settings Sync (the company laptop is signed in to a company account).
- R4.8 Changes can be pushed from any machine, including the work laptop, without logging in to the personal GitHub account there: the work laptop uses a credential limited to this one repo. Auto-push is on for personal machines and off on the work laptop (review, then push by hand).

### R5 — Secrets and identity

- R5.1 No secret is committed. Today no secrets need managing: GitHub auth is held by gh. Anything that needs a GitHub token reads it from `gh auth token`.
- R5.2 One git identity per machine (name and email asked on first run): personal identity on personal machines, company identity on the work laptop. No per-directory identity switching.
- R5.3 GitHub access through `gh`, logged in to the hosts the machine uses (github.com on personal machines; the enterprise host on the work laptop, plus github.com only if needed). gh is git's credential helper, so git uses HTTPS. No `hub`, no SSH keys for GitHub.

### R6 — macOS settings

- R6.1 iTerm2 is the main terminal. Its profiles are Dynamic Profiles (JSON, one file per colour scheme, sharing a base profile), and its global settings load from a folder in the repo. Both are synced through the repo. (Profile layout and the per-machine default: `0.2.0_ITERM_PROFILES.md`.)
- R6.2 Italics and true colour work in iTerm, tmux and Neovim. Since task 41 (ADR 0009) macOS's own `xterm-256color` and `tmux-256color` entries cover italics, so nothing is compiled; true colour comes from iTerm's `COLORTERM=truecolor` and tmux's `Tc` override.
- R6.3 Room for more `defaults write` settings (Dock, Finder, keyboard repeat…), grouped like packages.
- R6.4 iTerm2's generative AI features are disabled on every machine.
- R6.5 Every font used by an iTerm profile is installed automatically (IntoneMono Nerd Font is the default).

## Non-functional requirements

- N1 No custom installer framework or logger; custom scripts are short, idempotent shell.
- N1.1 No Ruby to write or maintain.
- N2 A dry run shows what would change before applying.
- N3 Tested on a clean macOS VM for both profiles before a release.
- N4 The README documents bootstrap, profiles, adding a package, adding a dotfile and troubleshooting (ported from vizion's README).

## Out of scope for 0.1.0

- Docker, and the tools dropped in the cleanup (see the design's cleanup table).
- SSH key generation (pending a check that anything still needs SSH).
- A `~/Developer` directory convention (dropped; gh handles the cloud/enterprise split).
- Secrets management (none needed today; revisit if one appears, e.g. the Homebrew API token).
- Linux support.
- Pinned package versions / rollbacks.
- Automatic uninstall of deselected groups.
