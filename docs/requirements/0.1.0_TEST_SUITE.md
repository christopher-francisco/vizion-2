# 0.1.0 — Test suite

- **Status:** Accepted (2026-10-15). Turns the one-off checks from tasks 13, 25 and 26 into a repeatable regression suite. Tooling in ADR 0005.

## Goals

1. After a batch of changes, one command tells me whether both profiles still provision a clean Mac.
2. Checks fail loudly: every check passes or fails on its own; nothing is read by eye.
3. The steps only a person can do (GitHub logins, token creation, GUI checks) are part of the run: the suite pauses for them and verifies the result.

## Why

- Task 13 was driven by scripts in `~/.cache/vizion-2-vmtest/` (outside the repo, hard-coded IPs and password) and can't be re-run without redoing the setup.
- Its `verify.sh` only printed output, and two checks were wrong without anyone noticing: tmux plugins looked up in `~/.tmux/plugins` (they're in `~/.config/tmux/plugins`), and treesitter parser counts (0/17) that don't match the 36 the apply reported.
- The gh login and push-token scripts were tested against stubs, by hand, each time they changed. The real flows have never run end to end.

## Constraints

- Run on demand, as a regression pass after a batch of changes. No git hook, no CI (GitHub's macOS runners can't run nested VMs).
- Shell scripts, plus `expect` (preinstalled on macOS) to answer the interactive first-run questions. No other new dependency besides Tart.
- Lives in the repo under `test/`, never applied to `$HOME` (`.chezmoiignore`). No secrets: the repo is public.
- Never touches the host's real `$HOME`, Keychain, tmux server or iTerm prefs: temp homes, `unset TMUX` and a private `-S` tmux socket.

## Functional requirements

### T1 — Entry point

- T1.1 `test/run.sh [scenario…]` runs the host checks (T2), then each VM scenario (T3), then the guided steps (T4). With no arguments it runs `personal` and `work`.
- T1.2 `--unattended` skips the guided steps (also skipped, with a notice, when `run.sh` has no terminal). `--host-only` skips the VMs.
- T1.3 Up to two VMs run at once (macOS allows two macOS guests per host), so `personal` and `work` run side by side.
- T1.4 Results go to `test/out/<timestamp>/` (gitignored): per-scenario logs, plus a summary listing each check as `ok`/`not ok`. Exit code is non-zero if any check failed.

### T2 — Host checks (seconds, no VM)

- T2.1 Render every template for each fixture config (`test/fixtures/<scenario>.toml`) and compare `chezmoi managed`/`ignored` against a temp destination with the expected lists.
- T2.2 `bash -n` and `shellcheck` on every rendered script.
- T2.3 The rendered Brewfile parses (`brew bundle list`), and every name in it exists.
- T2.4 `.chezmoidata/*.yaml` loads, and every group it names exists in `.chezmoi.toml.tmpl`.
- T2.5 Script tests with stubs on `PATH` (`gh`, `security`), TTY cases through `expect`:
  - `50-gh-auth`: logged out with and without a terminal, failed login, login, already logged in, env tokens never reach gh.
  - `55-work-push-token`: skip, store, mismatched retype then store, already stored, no terminal.

### T3 — Clean-VM run (unattended)

- T3.1 Each scenario clones a vanilla Sequoia image pinned by digest, removes CLT and passwordless sudo, and deletes the VM at the end (`--keep` keeps it).
- T3.2 Source under test: the working tree by default (uncommitted changes included), copied into the VM as `~/.local/share/chezmoi`, and the README one-liner runs without the repo argument; so changes are tested before pushing. (chezmoi's built-in git can't clone a local path without the Command Line Tools.) `--from-github` runs the full one-liner against `main` instead.
- T3.3 The first run answers the questions from the scenario's fixture with `expect` and interrupts the gh browser login (left to T4), which stops that apply; a second apply without a terminal finishes it.
- T3.4 `test/assert.sh` runs in the VM. Expected values are read from the repo, not hard-coded:
  - a second apply exits 0 and prints only the expected notices; `chezmoi status` is empty; the source clone has no changes (lock files not rewritten)
  - `brew bundle check` against the rendered Brewfile
  - asdf versions match `.tool-versions`
  - tmux plugins match the `@plugin` lines in the tmux config
  - for each nvim config, every `lazy-lock.json` entry is installed at its locked commit; Mason packages match the expected list (moved into `test/`); treesitter parsers match LazyVim's `ensure_installed`
  - iTerm prefs-folder keys are set, Dynamic Profiles links match `linked/iterm2/DynamicProfiles/*`, terminfo entries resolve
  - git identity and the credential helper for each URL (`git config --get-urlmatch`) match the profile
  - `zsh -ic` starts without errors and the aliases exist
- T3.5 `--fast` starts from a cached image with CLT and Homebrew already installed, rebuilt when the pinned digest or `00-prereqs` changes. The clean run stays the default.

### T4 — Guided steps (human in the loop)

- T4.1 After T3, the VM stays up with its window open (`test/guided.sh`, one VM at a time after each pair). The suite notifies the host, prints one step at a time, waits for Enter, then checks the result over SSH (`test/vm/guided-assert.sh`).
- T4.2 The apply that needs a person runs in the VM's Terminal app, not over SSH, so the login Keychain is the real one (over SSH, gh can quietly save its token to a plain-text file). The suite opens it itself (`open -a Terminal` on a generated `.command` file, recorded with `script`); the SSH checks unlock the login Keychain first, since it's locked in SSH sessions.
- T4.3 gh login (profiles that log in to github.com): enter the device code at github.com/login/device in the host browser. Verify: `gh auth status`, token stored in the Keychain and not in `hosts.yml`, git gets gh's token for the repo URL, and `git push --dry-run` of a new branch works over HTTPS (`ls-remote` would pass without credentials: the repo is public). `~/.gitconfig` still matches chezmoi (`chezmoi verify`), in case gh offers to set up git.
- T4.4 Work scenarios: create a fine-grained token (vizion-2 only, Contents read/write, 1-day expiry) and paste it at the `55-work-push-token` prompt. The host clipboard doesn't reach the VM, so the suite offers to put the token on the VM's clipboard (hidden input, `pbcopy` over SSH, cleared afterwards). Verify: Keychain item exists, git gets it for the repo URL, `git push --dry-run` from the source succeeds, another github.com repo doesn't get the token.
- T4.5 Re-apply, in the VM's Terminal again: exits 0, and `50-gh-auth` and `55-work-push-token` print nothing (on `work`, except the failed login to the fixture's nonexistent enterprise host).
- T4.6 GUI checks (profiles with the `gui` group), answered y/n and recorded in the summary, with what the person saw on a no: iTerm opens on the dynamic default profile (name read from the repo), Option+Left/Right jump by word, Karabiner loads its config (its profiles listed). The suite opens each app.
- T4.7 Before deleting the VM, prints the cleanup steps: revoke the gh OAuth grant (GitHub → Settings → Applications; `gh auth logout` only forgets it locally; revoking logs out every gh of the account, so log in again on the host) and delete the test token. Then waits for Enter and deletes the VM (`--keep` keeps it).

### T5 — Scenarios

| Scenario | Covers |
|---|---|
| `personal` | Full personal profile |
| `work` | Work profile; CrowdStrike on; enterprise host `github.example.com` (logs in only to github.com) |
| `work-brew-first` | Like the laptop: Homebrew already installed with its own one-liner from brew.sh before the bootstrap, so `00-prereqs` skips it. Passes if the `sudo` prompts are only the expected ones (Homebrew's install, the `karabiner-elements` cask) |
| `upgrade` | Applies a known-good older commit, then the working tree: renamed scripts (task 25), `run_onchange` re-runs, `exact_` removals |

## Out of scope

- The real GitHub Enterprise login, MDM and CrowdStrike policies, and the corporate network. These are covered by a "first apply on the work laptop" checklist in the README.
- Intel Macs and macOS versions other than the pinned image.
