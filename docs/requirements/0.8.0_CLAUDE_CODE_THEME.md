# 0.8.0 — Claude Code follows the colour scheme and light/dark

- **Status:** Accepted and built (2026-10-25). Decision in ADR 0012. Builds on `0.3.0_COLOUR_SCHEME_SYNC.md` (ADR 0007). Board task 45.

## Goal

Claude Code in the terminal uses the Tokyonight or Everforest colours, in light or dark, matching the iTerm window it runs in, as tmux and Neovim do. Inside tmux, Claude Code switches when tmux does (attach, focus, appearance). Outside tmux, it switches at the next prompt. No restart.

Before: `"theme": "auto"`: Claude Code's built-in dark or light preset, from the terminal's background.

## Findings (Claude Code 2.1.310, checked 2026-10-25)

- **Custom themes** ([docs](https://code.claude.com/docs/en/terminal-config#create-a-custom-theme)) are JSON files in `~/.claude/themes/<slug>.json`: `name`, `base` (a built-in preset: `dark`, `light`, …), `overrides` (colour tokens → `#rrggbb`, `rgb()`, `ansi256()`, `ansi:<name>`). Unknown tokens and bad values are ignored. Selected as `"theme": "custom:<slug>"`. The `theme` key is in `~/.claude/settings.json` (schema: `auto`, the six presets, or `custom:*`).
- **Live reload:** Claude Code watches `~/.claude/themes/` and reloads every running session when a file is added or changed. If the folder didn't exist when a session started, that session needs one restart.
- **A custom theme doesn't follow light/dark.** `auto` resolves to the system theme only for the built-in presets. A custom theme resolves to its own fixed `base` (`tZt` in the bundle: `auto` → system theme, preset → itself, `custom:x` → x's base). So two custom themes can't be paired the way `auto` pairs `dark` and `light`.
- An all-`ansi:` theme would take the iTerm window's own palette, per window and per appearance, with no sync at all. But the backgrounds (diffs, your messages, selection) can only be the 16 ANSI colours: loud blocks, nothing like the schemes. Rejected (ADR 0012).
- **Hooks** run with the session's environment (`TMUX`, `ITERM_PROFILE`), and their stdin is a JSON event. A `UserPromptSubmit` hook's stdout is added to the conversation, so the hook must print nothing.

## Design

- **Palettes** `dot_claude/vizion/themes/<scheme>-<dark|light>.json` (→ `~/.claude/vizion/themes/`), one per scheme and appearance, base `dark` or `light`, about 70 tokens from the same palettes as the tmux themes (Tokyonight Night/Day, Everforest soft dark and light; `claude` is the scheme's orange). Backgrounds (diffs, messages) are the scheme's colours laid over its background. They sit outside `~/.claude/themes/`, so `/theme` doesn't list them.
- **The active theme** `~/.claude/themes/vizion.json` is the one Claude Code loads (`custom:vizion`). chezmoi creates it once (`create_`, the answer's `-dark`); from then on `theme.sh` owns it, so an apply never undoes the sync.
- **`~/.claude/vizion/theme.sh [<scheme> <dark|light>]`** (rendered: the profile → scheme table from `colour-schemes.json`, like tmux's hook) copies the palette over `vizion.json`, in one rename, only when it differs. It never fails and prints nothing. It picks:
  - with arguments: those (from tmux's hook);
  - inside tmux: tmux's `@theme`;
  - outside tmux: the window's `ITERM_PROFILE` through the table (`This Mac` and other terminals → the `theme` answer), in the macOS appearance (`defaults read -g AppleInterfaceStyle`: `Dark`, or missing in light mode). iTerm's light/dark follows the system's.
- **tmux's `theme.sh`** calls it with the window in use's scheme and appearance on every event, before its own "already applied" check: a Claude outside tmux may have taken the file over since. An unchanged file costs one `cmp`.
- **Claude Code's hooks** `SessionStart` and `UserPromptSubmit` run it with no arguments. A new session starts right, and a session outside tmux catches up at the next prompt.
- **`~/.claude/settings.json`** stays the machine's own. A `modify_` script sets `"theme": "custom:vizion"` and adds the two hooks if they're missing, with jq (key order kept). Missing file → created. No jq yet, or not JSON → left as it is. Picking another theme in `/theme` lasts until the next `chezmoi apply`.

## Tests

- **Host** (`test/host/47-claude-theme.sh`): every scheme has a dark and a light palette on the matching base, with the same tokens, all `#rrggbb`. The created `vizion.json` is the answer's dark palette. The rendered `theme.sh` (shellcheck, then run against a stub `tmux` and `defaults`) picks each iTerm profile's scheme in both appearances outside tmux (`This Mac`, no profile → the answer), tmux's `@theme` inside tmux (the window when tmux has none yet), its arguments, and writes nothing for an unknown scheme, printing nothing each time. tmux's hook hands it the window's scheme. The settings merge keeps other keys and hooks, adds the theme and both hooks once, a second run changes nothing, a missing file is created, and non-JSON or no jq leaves the file alone. Mutation-checked: five planted breaks (appearance, tmux ignored, hooks added twice, theme not set, tmux's argument) were each caught.
- **On this Mac** (2026-10-25): applied the Claude Code files. `settings.json` kept its cc-status hooks and gained the theme and both hooks. Run outside tmux in light mode, `theme.sh` wrote Everforest Light (`This Mac` → Everforest). `chezmoi diff` stays clean after the rewrite.
- **Left, by hand:** a new Claude Code session shows the scheme (sessions started before `~/.claude/themes/` existed need one restart). An appearance flip shows at the next prompt outside tmux, and at once inside tmux. Attaching from a Tokyonight window recolours a running Claude in tmux.

## Not covered

- Several Claude sessions in windows of different schemes share one theme file: the last window to act wins (tmux has the same limit, its options being global). Outside tmux, a session catches up at its next prompt.
- A light/dark flip outside tmux shows at the next prompt, not at once: nothing runs on the flip itself.
- Claude Code outside iTerm (VS Code's terminal, Neovide) gets the `theme` answer.
