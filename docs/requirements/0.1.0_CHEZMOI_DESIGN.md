## Syncing configs across machines

Sync always goes through the git repo, whatever the file mode: commit and push on one machine, then `chezmoi update` (git pull + apply) on the others. On personal machines `git.autoCommit` and `git.autoPush` are on, so every `chezmoi edit`/`re-add` is pushed automatically. On the work laptop both are off: changes are reviewed with `chezmoi diff` / `git diff` and pushed by hand (see "Pushing from the work laptop").

**Rule: copy by default, as chezmoi intends; symlink only what an app rewrites itself.** This follows chezmoi's guide ("Handle configuration files which are externally modified"), whose worked example is exactly VS Code's `settings.json`. chezmoi's global "symlink mode" is not used. Decided in ADR 0003.

- **Copied files (default)**: everything you edit yourself, including both Neovim configs. Edit with `chezmoi edit --apply <file>` (add `--watch` to re-apply on every save, so Neovim sees changes immediately), or edit the file in place and run `chezmoi re-add <file>`. `chezmoi status`/`chezmoi diff` show what drifted; `chezmoi apply` asks before overwriting a local edit. Templates (gitconfig, tmux.conf) can only be edited with `chezmoi edit`.
- **Symlinked files**: files an app rewrites on its own. The real file lives in `linked/` (listed in `.chezmoiignore`), and a `symlink_<name>.tmpl` whose whole content is `{{ .chezmoi.sourceDir }}/linked/<path>` makes the target a link to it, so the app's changes land in the repo's working tree. Used for:
  - VS Code `settings.json`, `keybindings.json` (one symlink per file).
  - `lazy-lock.json` of each Neovim config (rewritten by lazy.nvim on update/restore).
  - `~/.config/karabiner`, as a **folder**: Karabiner's docs require linking the folder, not `karabiner.json`, or it stops detecting config changes. `automatic_backups/` is git-ignored.
- **iTerm2 global settings need no symlink**: iTerm's own "Load preferences from a custom folder" setting points straight at `<source>/linked/iterm2` (`PrefsCustomFolder`, set by the macOS settings script from `{{ .chezmoi.sourceDir }}`).

Verify during the port that VS Code and lazy.nvim write through the symlink instead of replacing it with a regular file; if one doesn't, that file falls back to copy + `chezmoi re-add`.

Daily loop: edit (via `chezmoi edit`/`re-add` for copied files) → push (automatic on personal machines, by hand on the work laptop); `chezmoi update` on the others (or a shell alias / launchd job that runs it).

## Neovim: two configs side by side

Neovim reads its config from `~/.config/$NVIM_APPNAME`, defaulting to `~/.config/nvim` (plugins and state go to `~/.local/share/$NVIM_APPNAME` etc., so the two never share plugins).

| Config | Source in vizion | Target | How to launch |
|---|---|---|---|
| **LazyVim** (default) | branch `lazyvim`, `directories/.config/lazyvim/` | `~/.config/nvim` | `nvim` |
| **Legacy** | `master`, `directories/.config/nvim/` | `~/.config/nvim-legacy` | `NVIM_APPNAME=nvim-legacy nvim`, aliased `nvim-legacy` |

The default config sits at the plain `~/.config/nvim` path rather than at `~/.config/lazyvim` with `export NVIM_APPNAME=lazyvim`. That way every caller gets LazyVim, including the ones that don't go through zsh (git's `core.editor`, `$VISUAL` from GUI apps, `sudoedit`). The `lazyvim` alias from the branch is no longer needed. The legacy dir is called `nvim-legacy` rather than `legacy` so `~/.config/` and `~/.local/share/` stay readable.

Both are normal copied chezmoi files (`dot_config/nvim/…`, `dot_config/nvim-legacy/…`): edit them with `chezmoi edit --apply` (or `--watch`) or edit in place and `chezmoi re-add`. Only each config's `lazy-lock.json` is a symlink into `linked/`, because lazy.nvim rewrites it on plugin updates. The plugin restore script runs for both: `nvim --headless "+Lazy! restore" +qa` and the same with `NVIM_APPNAME=nvim-legacy`.

## tmux

`tmux.conf` merges both vizion branches (they touched different lines):

- From `master`: `set -g default-command "reattach-to-user-namespace $SHELL"`, the workaround for tmux 3.5a + tmux-sensible not loading the zsh config. `reattach-to-user-namespace` stays in the `core` group.
- From `lazyvim`: `set -g @yank_action 'copy-pipe'` (tmux-yank no longer scrolls to the bottom after copying).
- From `lazyvim`, **only when `.machine.crowdstrike` is true** (defaults to on for the `work` profile): the `vim-tmux-navigator` tmux plugin is replaced by inlined Ctrl-h/j/k/l and `C-\` bindings whose `is_vim` check only looks at the current pane's tty, because CrowdStrike flags the plugin's machine-wide `ps` scan ([issue #428](https://github.com/christoomey/vim-tmux-navigator/issues/428#issuecomment-2629247163)). The tmux < 3.0 `bc` version check and the old commented-out `is_vim` are dropped. Other machines keep `set -g @plugin 'christoomey/vim-tmux-navigator'`.

The file becomes `dot_config/tmux/tmux.conf.tmpl`:

```tmux
{{ if .machine.crowdstrike -}}
# CrowdStrike flags vim-tmux-navigator's `ps` scan; inline its bindings with a per-pane check instead.
is_vim="ps -o tty= -o state= -o comm= | grep -iqE '^#{s|/dev/||:pane_tty} +[^TXZ ]+ +(\\S+\\/)?g?(view|l?n?vim?x?|fzf)(diff)?$'"
bind-key -n 'C-h' if-shell "$is_vim" 'send-keys C-h' 'select-pane -L'
bind-key -n 'C-j' if-shell "$is_vim" 'send-keys C-j' 'select-pane -D'
bind-key -n 'C-k' if-shell "$is_vim" 'send-keys C-k' 'select-pane -U'
bind-key -n 'C-l' if-shell "$is_vim" 'send-keys C-l' 'select-pane -R'
bind-key -n 'C-\' if-shell "$is_vim" 'send-keys C-\\' 'select-pane -l'
bind-key -T copy-mode-vi 'C-h' select-pane -L
bind-key -T copy-mode-vi 'C-j' select-pane -D
bind-key -T copy-mode-vi 'C-k' select-pane -U
bind-key -T copy-mode-vi 'C-l' select-pane -R
bind-key -T copy-mode-vi 'C-\' select-pane -l
{{- else -}}
set -g @plugin 'christoomey/vim-tmux-navigator'
{{- end }}
```

Both Neovim configs keep the Neovim side of `vim-tmux-navigator`, so navigation works either way.

## Shell (`.zshrc`, `.zshrc.aliases`)

**`.zshrc` is managed by chezmoi** (`dot_zshrc`). vizion let the oh-my-zsh installer create `~/.zshrc` and then appended a `source` line; here chezmoi downloads oh-my-zsh as an external instead of running its installer, so nothing else would create the file. It stays short:

```zsh
export ZSH="$HOME/.oh-my-zsh"
ZSH_THEME="robbyrussell"
plugins=(git)
source $ZSH/oh-my-zsh.sh
source ~/.zshrc.aliases
```

`.zshrc.aliases` keeps holding everything else (PATH, exports, aliases, functions), as today. Machine-specific lines go in `~/.zshrc.aliases.local`, which is not managed and is created empty if missing (existing behaviour). Installers that append to `~/.zshrc` (pnpm, bun…) show up as drift in `chezmoi diff`; move what's worth keeping to the `.local` file. The pnpm and bun lines in today's `~/.zshrc` are not ported (bun is dropped; pnpm comes from corepack per project).

`.zshrc.aliases` is merged from both vizion branches:

- `~/.local/bin` goes **first** on the `PATH` (master's version), so chezmoi, Claude Code and other user-installed tools win over same-named ones.
- **asdf** manages language runtimes: its shims go on the `PATH` (from master), `asdf` is in the `dev` group, and chezmoi manages `~/.tool-versions` (today: `nodejs 24.3.0`). `n` and `N_PREFIX` are dropped.
- **fzf** key bindings and completion via `source <(fzf --zsh)` (replaces the branch's `source $(brew --prefix fzf)/shell/key-bindings.zsh`). `fzf` is added to `core`; it was missing from the Brewfile, so the branch line and the `vs`/`nvs` aliases only worked where fzf had been installed by hand.
- **hub is gone:** drop `alias git=hub`, `HUB_PROTOCOL`, and the `chpwd`/`setGithubVersion` hook that swapped `GITHUB_TOKEN`/`GITHUB_HOST` per folder. See "GitHub access".
- `alias lazyvim=…` → `alias nvim-legacy='NVIM_APPNAME=nvim-legacy nvim'`; `alias vizion` → `chezmoi cd`.
- `~/.zshrc.tokens` and its `source` line are dropped: every token it held is gone (rhubarb, hub's per-host tokens) except `HOMEBREW_GITHUB_API_TOKEN`, which is a later board task (likely `export HOMEBREW_GITHUB_API_TOKEN=$(gh auth token)`, no stored secret).
- `mkdir -p ~/Developer/code/enterprise` is dropped (no directory convention any more).

## GitHub access

`gh` replaces `hub` and SSH for GitHub:

- `gh auth login` for the hosts the machine uses: github.com on personal machines, `gh auth login --hostname <enterprise host>` on work machines (github.com there only if needed). gh stores the tokens in the macOS Keychain and handles several hosts, so no per-folder token switching is needed.
- `gh auth setup-git` makes gh the git credential helper, so clone/pull/push run over HTTPS with those tokens. On personal machines that includes chezmoi's own repo (`chezmoi update`, `git.autoPush`). On the work laptop it is set up for the enterprise host only (`gh auth setup-git --hostname <enterprise host>`), so github.com credentials for this repo come from the repo-scoped token below.
- `gh config set git_protocol https`.
- Tools that need a raw token read it with `gh auth token [--hostname …]` rather than a stored copy.

### Pushing from the work laptop

The work laptop is not logged in to the personal GitHub account. To push this repo from it, it uses a **fine-grained personal access token scoped to `christopher-francisco/vizion-2` only**, with the single permission "Contents: read and write" and an expiry date. If the laptop is lost or wiped, the token can touch nothing but this repo.

- `dot_gitconfig.tmpl` adds, on work machines only, a credential entry bound to this repo's URL:

  ```ini
  {{ if eq .profile "work" -}}
  [credential "https://github.com/christopher-francisco/vizion-2.git"]
      helper = osxkeychain
      useHttpPath = true
  {{- end }}
  ```

- First push: git asks for username + password; the password is the token. macOS Keychain stores it (git's `osxkeychain` helper) and git doesn't ask again until it expires. The token is entered by hand once; it is not managed by chezmoi and never touches the repo.
- Auto-commit and auto-push are off on the work laptop. The loop there is: edit → `chezmoi diff` → `chezmoi cd` → `git commit` → `git push`.
- Pulling needs no token if the repo is public; if it's private, the same token covers it.
- Company-specific values (enterprise host, work email, CrowdStrike flag) are first-run answers stored in that machine's `~/.config/chezmoi/chezmoi.toml`, never in the repo, so a push from the work laptop only carries edits to shared files.
- Renewal: when the token expires, create a new one with the same scope and remove the old Keychain entry (`git credential-osxkeychain erase`, or Keychain Access). The README documents both steps.
- Check company policy before using it: if pushing from a company machine to a personal remote is not allowed, the work laptop stays pull-only.

SSH keys are **not** generated in 0.1.0. Whether anything still needs SSH (non-GitHub servers, commit signing) is a separate board task.

## VS Code

Installed by the `visual-studio-code` cask (`gui` group). Its settings and extensions are managed by this repo, **not** by VS Code Settings Sync: on the company laptop VS Code is signed in to the company account, and Sync would either mix personal and company settings or not apply at all.

- `settings.json` and `keybindings.json` live in `linked/vscode/` and are symlinked one by one into `~/Library/Application Support/Code/User/`. Only those files are linked, never the whole `User/` folder, which also holds caches and workspace state. Changes made in VS Code's settings UI land in the repo. Verify during the port that VS Code writes through the symlink rather than replacing it; if it doesn't, fall back to copy mode + `chezmoi re-add`.
- Extensions are listed under `packages.gui.vscode`; `run_onchange_after_25-vscode-extensions.sh.tmpl` runs `code --install-extension <id>` for each, so adding an ID re-runs it. After installing an extension from the UI, add its ID to the list (`code --list-extensions` prints them). The list can differ per profile if the company restricts extensions.
- Settings Sync stays off on every machine (it's off unless turned on); the README says so.
- The old `vscode/install.sh` and `vscode/extensions` are not ported: the script was broken (it installed a literal `extension` and symlinked a relative path) and the list was outdated. The list is rebuilt from what's installed today, pruned.

## iTerm2

Decided in ADR 0002. Source: the `lazyvim` branch's plist for everything about profiles, fonts and colours; nothing from `master`'s WIP commit (its AI settings and the Menlo font switch are dropped).

- **Profiles → Dynamic Profiles.** A one-off port script converts the 17 profiles of the `lazyvim` plist into JSON under `~/Library/Application Support/iTerm2/DynamicProfiles/`: a `Base` profile in `00-base.json` with the shared settings, then one file per colour scheme whose profiles only override colours, font, size and spacing. Duplicate names are renamed (`Tokyonight (Night)` 16pt → `Tokyonight (Night) - 5k`, `Everforest Dark` 16pt → `Everforest Dark - 4k`). GUIDs are kept so the default stays `Tokyonight (Night) - 4k small`. Change profiles by editing the JSON (`chezmoi edit --apply`); iTerm reloads it, and changes made in its UI are not saved back.
- **Slim main plist, read from the repo.** iTerm's "Load preferences from a custom folder" points at `<source>/linked/iterm2` (no `~/.iterm2`, no symlink); changes made in iTerm's global settings land in the repo. `linked/iterm2/com.googlecode.iterm2.plist` keeps global settings only: no profiles, no `AI*`/`Ai*` keys, no window state. `Default Bookmark Guid` points at the default dynamic profile.
- **AI off.** iTerm's switch for all generative AI features is the advanced setting `GenerativeAIAllowed`. It is set to `false` in the slim plist, and the macOS settings script also runs `defaults write com.googlecode.iterm2 GenerativeAIAllowed -bool false`. The API server (`EnableAPIServer`) stays off.
- **Fonts.** Profiles use IntoneMono Nerd Font (`IntoneMonoNF`, the default), MesloLGS DZ Nerd Font Mono and FiraCode. They are installed by the casks `font-intone-mono-nerd-font`, `font-meslo-lg-nerd-font` and `font-fira-code-nerd-font` (all verified to exist). A missing IntoneMono is the likely reason `master` fell back to Menlo.
- **Stale font names.** `One Dark - 4k` uses `FiraCodeNerdFontComplete-Regular` and `Rigel - 4k` uses `FuraCodeNerdFontComplete-Retina`, names from Nerd Fonts v1/v2 that current casks don't provide. Map them to the v3 names during the port or drop those profiles.
- **Key maps.** The `lazyvim` profiles drop 36 per-profile key mappings (Ctrl-2…8, Shift/Ctrl+arrows, Home/End, Shift+F-keys). Check Ctrl+arrows in Neovim and tmux after the port.
- `.itermcolors` files are no longer needed for setup (colours live in the JSON).

## Profiles and groups

First run asks a few questions, stored in `~/.config/chezmoi/chezmoi.toml`:

```toml
{{- $profile := promptChoiceOnce . "profile" "Machine profile" (list "personal" "work") -}}
{{- $isWork := eq $profile "work" -}}
[data]
  profile = {{ $profile | quote }}
  name = {{ promptStringOnce . "name" "Git name" | quote }}
  email = {{ promptStringOnce . "email" "Git email for this machine" | quote }}
  [data.groups]
    core = true
    dev = true
    gui = {{ promptBoolOnce . "groups.gui" "Install GUI apps (iTerm, VS Code, Karabiner…)" true }}
    personal = {{ promptBoolOnce . "groups.personal" "Install personal apps (1Password, Spotify)" (not $isWork) }}
    mas = {{ promptBoolOnce . "groups.mas" "Install Mac App Store apps (needs Apple ID sign-in)" (not $isWork) }}
    enterprise = {{ promptBoolOnce . "groups.enterprise" "Log gh in to a GitHub Enterprise host" $isWork }}
  [data.machine]
    crowdstrike = {{ promptBoolOnce . "machine.crowdstrike" "Is CrowdStrike installed (inline tmux navigator bindings)?" $isWork }}

[git]
  autoCommit = {{ not $isWork }}
  autoPush = {{ not $isWork }}
```

The profile only supplies defaults; each group is still a yes/no, so a company laptop can be `work` with, say, `gui` on and `mas` off. To change answers later: `chezmoi init --prompt` (or edit `chezmoi.toml`) then `chezmoi apply`.

## Secrets and git identity

**No secrets to manage.** After the cleanup nothing in the setup needs one: GitHub tokens live in gh (Keychain), rhubarb/grip/hub tokens are gone with their tools, and `HOMEBREW_GITHUB_API_TOKEN` is a later task that can read `gh auth token`. So there is no 1Password or Keychain integration, no `.zshrc.tokens`, and no `secrets_1password` group. If a real secret shows up later, chezmoi's `onepasswordRead` (personal) / `keyring` (work) template functions are the way to add it.

**One git identity per machine.** `dot_gitconfig.tmpl` writes `[user]` from the `name`/`email` answered on first run: personal email on personal machines, company email on the work laptop. This replaces `scripts/setup_gitconfig.sh`, `~/.gitconfig.local`, `~/.gitconfig.enterprise` and the `includeIf "gitdir:~/Developer/code/enterprise/"` block. Because it's a template, `~/.gitconfig` is a rendered copy, not a symlink (chezmoi can't symlink a file whose content differs per machine). The shared parts (delta, core.editor, LFS, excludesfile) live in the same template, so a change to them is made in the repo (`chezmoi edit ~/.gitconfig`), not with `git config --global`, which would write to the copy and show up as drift.

## Externals

`.chezmoiexternal.toml` fetches third-party code that vizion vendors today:

```toml
[".oh-my-zsh"]
  type = "archive"
  url = "https://github.com/ohmyzsh/ohmyzsh/archive/master.tar.gz"
  exact = true
  stripComponents = 1
  refreshPeriod = "168h"

[".config/tmux/plugins/tpm"]
  type = "git-repo"
  url = "https://github.com/tmux-plugins/tpm"
  refreshPeriod = "168h"
```

The vendored `.config/tmux/plugins/*` and `.vim/autoload/plug.vim` are removed from the repo.

`exact = true` makes chezmoi delete anything in `~/.oh-my-zsh` that isn't in the archive, so `.oh-my-zsh/cache/**` (written by oh-my-zsh at runtime) is in `.chezmoiignore`, and custom themes or plugins can't live in `~/.oh-my-zsh/custom`. oh-my-zsh's own updater is turned off in `.zshrc` (`zstyle ':omz:update' mode disabled`): the archive isn't a git checkout, and chezmoi refreshes it every 168h.
