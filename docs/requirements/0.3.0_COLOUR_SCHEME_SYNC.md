# 0.3.0 — Colour scheme and light/dark: tmux and Neovim follow the iTerm window

- **Status:** Accepted and built (2026-10-16). Decision in ADR 0007. Builds on `0.2.0_ITERM_PROFILES.md` (ADR 0006); replaces its `iterm.theme` answer with a top-level `theme`. Board tasks 36 (idea) and 38 (build).

## Goal

tmux and Neovim take their colour scheme (Tokyonight or Everforest) and light/dark from the iTerm window in use. The flow: open a new iTerm window with another profile (Profiles menu) or appearance, `tmux attach`; tmux and the running Neovims recolour to match. Going back to an older window that's still attached switches back to its scheme. No restart and no `THEME` variable. The first-run answer `theme` is the machine's scheme: `This Mac`'s, and the fallback until a window says otherwise.

Before: tmux hard-sourced Tokyonight Night and never changed; LazyVim was always Tokyonight (Everforest installed, never picked); the legacy config hard-coded Tokyonight. Neovim already followed iTerm's light/dark (below), since `THEME` was dropped in 0.2.0.

## Findings (checked 2026-10-16)

### iTerm announces light/dark, not a scheme

iTerm 3.7.5 (absent in 3.6.0) implements mode 2031, Contour's [colour palette update notifications](https://github.com/contour-terminal/contour/blob/master/docs/vt-extensions/color-palette-update-notifications.md). An app enables it with `CSI ? 2031 h`; iTerm sends `CSI ? 997 ; 1 n` (dark) or `CSI ? 997 ; 2 n` (light) when the session's **background crosses between dark and light** (`terminalIsInDarkMode` is the background's `isDark`, not the OS flag; sent from `PTYSession.m` `textViewBackgroundColorDidChangeFrom:to:`). `CSI ? 996 n` asks for the current state. So an appearance flip sends it, and so does a profile switch that changes darkness; **Tokyonight Night → Everforest dark sends nothing**.

The only scheme-change event is the iTerm Python API (`VariableMonitor` on a profile name, [example](https://iterm2.com/python-api/examples/theme.html)): the API server on, a script running all the time, and a channel into tmux and Neovim still to build. Rejected (ADR 0007), as ADR 0006 rejected it for fonts.

### tmux 3.8 and Neovim 0.12 follow light/dark already

- **tmux** sends `?2031h` and `?996n` to each client on attach (`tty.c`), runs the hooks `client-light-theme`/`client-dark-theme` on each change, re-reads the client's colours (OSC 10/11), and forwards `997` to every pane that enabled 2031 (`window_pane_send_theme_update`). `#{client_theme}` holds `dark`/`light`. Its own `theme` option has ten named colours per side, too few for our themes.
- **Neovim**'s TUI enables 2031 at startup; on `997` it re-asks OSC 11 and sets `'background'` (news-0.11, `_core/defaults.lua`); a loaded scheme reloads (Tokyonight → Day, Everforest → its light palette). If a config sets `'background'` itself, the autocmd is deleted at `VimEnter` and this stops for good.

Simulated with a script playing iTerm to real tmux and real Neovim (this Mac's configs): Neovim alone and inside tmux went Night → Day → Night and Everforest dark → light on each `997`; tmux's hooks fired at attach and on every flip.

### What reaches tmux and Neovim on attach

A session started from one window, attached from another, with one or several windows attached:

- tmux runs a light/dark hook on **every** attach, dark → dark included: a new client starts as "unknown". It has no format for the window's exact colour (`#{pane_bg}` stays `default`), but iTerm sets `ITERM_PROFILE` in each window, and `update-environment` copies it into the session on attach.
- Neovim gets **FocusGained** on every attach. Asked for OSC 11, tmux answers with an attached window's **exact** background (`rgb:3333/3c3c/4343` from an Everforest dark window), which names the scheme. But it's the **first** attached window's (`window_get_bg_client` walks the clients oldest first), not the one in use. Light/dark for panes likewise: the windows' shared verdict, else the first window's colour (`window_pane_get_theme`). Found on this Mac: three windows on one session, the oldest Tokyonight, so a Neovim opened in the new Everforest window came up Tokyonight while tmux was Everforest. One window at a time (the first simulation) hides it.
- tmux has a `client-focus-in` hook (with `focus-events on`), so it can follow the window in use. In any client hook, `#{client_pid}`/`#{client_theme}` describe tmux's *current* client, which can be another window; `#{hook_client}` names the one the hook fired for.

### Bug found on the way

LazyVim's `neanias/everforest-nvim` spec never applied its `opts` (`background = "soft"`, `italics`): lazy.nvim couldn't tell the main module from the repo name (`get_main` nil), so `setup` never ran and Everforest rendered `medium` (`#2d353b`) instead of soft (`#333c43`, iTerm's). Fixed with `main = "everforest"`.

## Design

### The scheme data, from the iTerm profiles

`.chezmoitemplates/colour-schemes.json` reads `linked/iterm2/DynamicProfiles/*.json` and renders each scheme's dark and light background (the theme profile's `Background Color (Dark)`/`(Light)`, as `#rrggbb`) and the scheme of every profile (a theme profile's own, lower case; a size profile's parent's):

```json
{ "schemes": { "everforest": { "dark": "#333c43", "light": "#e5dfc5" }, "tokyonight": { "dark": "#1a1b26", "light": "#e1e2e7" } },
  "profiles": { "Everforest": "everforest", "Everforest 13": "everforest", …, "Tokyonight 20": "tokyonight" } }
```

A new theme profile reaches tmux and Neovim with no change to either.

### First-run answer `theme`

`Colour scheme (iTerm, tmux, Neovim)`, key `theme`, asked on every machine (tmux and Neovim need it without the GUI group). Choices: the iTerm theme profiles; default: the old `iterm.theme` answer if there is one, else `tokyonight`. A machine set up before runs `chezmoi update --init` (or `chezmoi init`) once and takes the default. `iterm.monitor` and `iterm.size` stay under `iterm`.

### tmux

- **Themes in pairs** under `dot_config/tmux/themes/`: `tokyonight-dark` (was `tokyonight-night`), `tokyonight-light` (the same file with tokyonight.nvim's Day palette), `everforest-dark` (was `everforest`, soft), `everforest-light` (Everforest light palette; replaces an old full-layout file of that name, unused). Each pair sets the same `@text_*`/`@bg_*`/`@border_*` options and nothing else; `minimal.tmux.conf` and the components read them at draw time, so re-sourcing one recolours tmux live.
- **`tmux.conf.tmpl`** sources `<theme>-dark` at startup (`@theme` set to match), turns `focus-events` on, adds `ITERM_PROFILE` to `update-environment`, and runs `~/.config/tmux/theme.sh <event> #{q:hook_client} [dark|light]` from four hooks: `client-attached` (`attached`), `client-focus-in` (`focus`), `client-dark-theme`/`client-light-theme` (`appearance`).
- **`theme.sh`** (rendered, `executable_theme.sh.tmpl`), per client:
  - `attached`: stores the session's `ITERM_PROFILE` (just copied from that window) as `@iterm_profile_<client>`, and makes the client the active one (`@active_client`).
  - `focus`: makes the client the active one.
  - `appearance`: only for the active client (a flip in a window not in use waits for its focus).
  - Then applies the client's scheme (its stored profile through the profile table; `This Mac`, other terminals → `theme`) in its light/dark (`#{client_theme}`; nothing yet right after attaching, the appearance hook follows): sources `themes/<scheme>-<dark|light>.tmux.conf`, records `@theme` (`tmux show -gv @theme`), and tells every Neovim in tmux, unless `@theme` already says so.
- On attach the status line shows the previous window's colours for under a second, until iTerm answers the light/dark query.
- tmux options are global: two windows on screen at once both show the active one's colours.

### Neovim

- **`lua/config/theme.lua`** (rendered in both configs from `.chezmoitemplates/nvim-theme.lua`): `{ default = <theme>, backgrounds = { everforest = { dark, light }, tokyonight = { … } } }`.
- **LazyVim** (`~/.config/nvim`): `opts.colorscheme = theme.default`; `lua/config/follow_terminal.lua`, set up from `options.lua`:
  - **Inside tmux, tmux decides.** At startup Neovim stores its server address in its pane's `@nvim_server` option (removed on exit), reads `@theme`, sets `'background'` and loads the scheme once the UI is up (after LazyVim's default). `theme.sh` calls `apply(scheme, appearance)` through `nvim --server` on every change, without waiting. Neovim's own light/dark following (its `TermResponse` autocmd in `nvim.tty`) is removed there: it would follow the first attached window.
  - **Headless** (`nvim --headless`: chezmoi's plugin sync, scripts): nothing is set up. Found on this Mac: `chezmoi apply` inside tmux failed loading `config.options`, because a headless Neovim has no `nvim.tty` group to take the light/dark following out of.
  - **Outside tmux, iTerm answers.** Asks for OSC 11 on `UIEnter` (Neovim's own startup query runs before the config) and `FocusGained`, and on each `TermResponse` loads the scheme whose background is **nearest** the answer (within 40 per channel, Euclidean; farther means another terminal, keep the scheme), unless it's already loaded. Nearest rather than exact because iTerm keeps Everforest's dark background in the P3 colour space and may convert it. Light/dark stays Neovim's own.
- **Legacy** (`nvim-legacy`): `M.colorscheme = theme.default`; doesn't follow the window (its lualine theme and lazy loading assume one scheme at startup).
- No config sets `'background'` at startup (host check; `follow_terminal.lua` sets it from tmux's choice on purpose).

## Tests

- **Host** (`test/host/46-colour-schemes.sh`): schemes read from the profiles; every scheme has a tmux dark/light pair setting the same options; no Neovim config sets `'background'`; `follow_terminal` in a headless Neovim inside tmux raises nothing; `follow_terminal.scheme_for` picks each scheme from its backgrounds (4- and 2-digit OSC 11 forms) and nothing for a grey or a foreground answer; per test profile, both `theme.lua` render the answer and every scheme's backgrounds, and the rendered `theme.sh` (shellcheck, then run against a stub `tmux` keeping options in files) sources each iTerm profile's scheme on attach, and the answer's for `This Mac`.
- **VM** (`test/vm/attach.py`, from `assert.sh`): tmux running Neovim (installed configs and plugins) and fake iTerm windows answering like iTerm 3.7 (`997`, OSC 10/11, DECRQM, focus reports, `ITERM_PROFILE` of a size profile). Steps: attach from a window of one scheme; attach from one of the other while the first stays attached; focus back and forth; start a second Neovim; flip the active window to light; flip the inactive one (no change); focus it; detach all and attach from `This Mac`. After each, tmux's `@theme` and every Neovim's `colors_name` and `'background'` are the window in use's. Run on this Mac against the rendered configs: 9/9; the one-window-at-a-time design failed its focus steps, as did keying on `#{client_pid}`.
- **Guided:** in the VM's real iTerm, `tmux new -s t nvim`, attach from an Everforest window, click back to the first window, then flip the appearance.

## Not covered

- A profile switched *inside* an attached window (Session → Edit Session, or a profile change of the same darkness): `ITERM_PROFILE` is only read on attach. Detach and attach again.
- Remote shells (ssh to another machine's tmux/Neovim).
